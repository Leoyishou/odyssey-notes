# 🪞Notes

查了官方源码和文档。**三者都通过缩小“下一次发给模型的上下文”来续聊，但压缩表示不同。** 也补充修正前面的说法：同一个 Codex harness，还会因服务端能力不同而走不同路径。

| Harness | 核心做法 |
|---|---|
| Codex | 原生压缩项，或文字摘要 |
| Claude Code | 模型写摘要，再重新装载必要材料 |
| Pi | 旧历史写成结构化摘要，近期原文保留 |

**1. Codex：有两条压缩路径**

支持原生压缩时，把历史送给服务端，得到一个带 `encrypted_content` 的**不透明压缩项**，后续请求携带它继续。它承载此前的关键信息和推理状态，不能当作一篇人类可读的总结；内部编码细节没有完全公开，也不能理解为可还原全部原文的压缩包。[官方说明](https://developers.openai.com/api/docs/guides/compaction)

另一条是**文字摘要路径**：给模型追加“生成任务交接摘要”的指令，要求保留进展、决策、约束、下一步和关键资料；再用摘要与预算内保留的用户消息重建上下文。这里的“本地压缩”指客户端组织流程，摘要仍需调用模型。[摘要源码](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs)

**2. Claude Code：单独调用模型写摘要**

接近窗口上限时，发起一次独立请求：携带要总结的历史，末尾追加摘要指令。它尽量复用原会话的提示缓存，降低这次调用的成本；完成后，以更短的上下文继续。[官方机制](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation)

压缩后不只剩摘要：系统提示仍生效，根 `CLAUDE.md`、记忆和计划等会重新加载，部分近期文件也会重读。因此，**磁盘上的长期规则，比只在早期聊天里提过一次的要求更容易持续生效**。[保留项说明](https://code.claude.com/docs/en/context-window#what-survives-compaction)

**3. Pi：最直观的“摘要＋近期原文”**

当前上游默认实现是：

- 接近窗口上限、剩余约 **16,384 tokens** 时触发。
- 从后往前保留约 **20,000 tokens** 的近期原文。
- 更早的历史交给当前模型，整理成目标、约束、进展、决策、下一步等结构化摘要。
- 下一次发送：**系统提示＋摘要＋近期原文＋新消息**。

再次压缩时，会用“上一份摘要＋新增历史”更新摘要。原始记录仍在追加式会话文件中。[官方文档与源码入口](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md)

**对你的 Bot，实际影响是：**压缩不会把知识写进模型参数。文字摘要路径会丢细节，反复更新摘要也可能累积遗漏；Codex 原生压缩同样不承诺原文无损。要可靠延续长期工作，需要同时保留**稳定规则、工作状态和可检索原记录**，不能只靠压缩摘要。

以上是当前上游机制；Cindy 绑定的版本、配置和插件可能调整阈值或具体行为。
