# 🪞Notes



“去 session 化”的意思是：**session 只用来承载计算，不再用来承载人的注意力。**

人不应该再去“看着某个 session”，只需要回应 agent 发出的**请求（ask）**。用 hook 还是用别的方式，只决定这些请求怎么产生、怎么投递。真正要设计的是三件事：

1. 什么情况下必须找人
2. 找人的时候给他什么
3. 人回应之后，session 怎么自己接着跑

## 注意力

### 1. 先按“谁来解锁”给 session 状态机分层

|     | 状态              | 如何判断 | 例子                 | 谁来解锁                          |
| --- | --------------- | ---- | ------------------ | ----------------------------- |
| 1   | Running         | 硬编码  | 正在执行               | 不需要                           |
| 2   | Blocked · 等机器   |      | 等外部事件、限流、等子任务完成    | **调度方**（定时、事件触发、superagent）   |
| 3   | Blocked · 等人    |      | 授权、缺 context、需要做决策 | **人**                         |
| 4   | Stopped · 达成目标  |      | 验证通过               | 人只需要知道结论，或者做验收                |
| 5   | Stopped · 未达成目标 |      | loop 停了，但目标没达成     | **先交给 superagent 判断**，不行再升级给人 |
| 6   | Failed          |      | 出错或预算耗尽            | superagent 判断要不要重试，否则升级给人     |

关键是第 5 种。“loop 停了”和“目标达成了”是两回事，要分开判断，就需要：
- **目标在启动时就带上验收标准**，机器才能自己检查有没有做到
- **有一个外部的监督者（superagent）**，它只做三件事：检查结果是否达标、决定重新规划或重启 loop、实在不行再升级给人。外力优先来自机器（superagent、定时、事件），人是最后一级兜底。同时要有预算和重试上限，防止机器之间互相踢皮球。


### 2. 【待处理】人只面对一种东西

把所有需要人的情况归成几类，每一类给最省力的交互：
- **授权**：一键同意或拒绝
- **补 context**：只问一个最小的问题（表单或选项），不要说“请看上文”
- **决策**：列出 2～3 个选项，并给出默认选项和超时策略（这个也可以下放，可逆操作，甚至不需要人决策，可以 AI 决策）
- **验收**：展示结果或 diff，人选通过、打回或改一下

每条 ask 都要自带这些信息：**目标、做了什么、卡在哪、需要你做什么、不回应会怎样**。判断标准是：**人不打开 session 也能处理完。** 只要他还得回去翻对话记录，就说明还没有真正去 session 化。

再往上做一层“注意力调度”：跨 session 合并同类请求（比如 5 个授权一次批完），排优先级，批量推送，减少打断次数。

### 3. 人回应之后，自动续跑

人在 inbox 里补完 context 或点了授权，这个回应应该自动注入原来的 session，让它恢复执行。人不需要“回到对话里说一句继续”。这样人和 session 的关系才算真正解开。

## 二、线性对话里怎么展示过去的 task

**最近t3code 可能在试一些叫收件箱的特性**

线性对话天然是按时间排的，但人关心的是状态。建议：
- **对话里放 task 卡片，而不是过程日志。** 过程默认折叠，卡片上只显示状态、结论和需要的动作。
- **task 是独立的对象，对话只是引用它。** task 的状态可以在对话之外继续变化，卡片实时更新，不靠追加新消息。
- **未闭环的 task 要能浮上来。** 在输入框附近固定一个区域，比如“2 个待验收 · 1 个待补 context”，而不是埋在第 37 条消息里。
- **人回来时先给一段摘要**，比如：“你不在的时候，完成了 3 个，1 个需要验收，1 个卡在缺 context。”

按你说的三类人来对应：
- **需要知道结论的** → 显示结论卡片，看完即可
- **需要验收的** → 显示 diff 加“通过 / 打回”按钮
- **需要补 context 的** → 显示一个最小问题加输入框

### 三、可调参数

1. **升级阈值**：什么时候 superagent 应该自己重试，什么时候该找人？大概取决于人的信息是不是不可替代，加上重试的成本和风险。
2. **默认行为**：人迟迟不回应时，agent 可以按默认继续、暂停，还是放弃？不同类型的 ask 应该有不同的默认值。
3. **验收标准由谁写**：一开始由人写，还是由 agent 起草、人确认？后者也算一个 ask。
4. **信任会累积**：同一类授权或验收多次通过后，能不能自动降级成“知悉”，让人越用越少被打断？




## cindy 的收件箱机制

Cindy 官方收件箱用**固定规则**给 session 分组。从上往下判断，**命中第一条就停止**。我核对的是你这台 Mac 已安装的 **0.1.141**。

| 优先级 | 判断条件 | 去哪里 |
|---|---|---|
| 1 | 已归档 | **已处理** |
| 2 | 选了「稍后处理」，指定时间还没到 | **稍后处理** |
| 3 | 宿主标记为等待处理，例如等你回答、等授权或运行出错 | **待处理** |
| 4 | 当前正在运行 | **进行中** |
| 5 | 是伙伴开的任务，且前面都没命中 | **从收件箱隐藏**，仍在任务列表里 |
| 6 | 有启用中的自动跟进，而且没有未读结果 | **进行中**，即使此刻没在跑 |
| 7 | 其余普通任务 | **待处理** |

**拿你的周三事项表举例。** 同样缺原表链接，子任务如果正式发起提问，就命中第 3 条，你会在「待处理」看到它。如果只在最终答复里写“缺链接”然后正常结束，就会命中第 5 条，从收件箱隐藏。甚至伙伴任务有未读结果，单凭未读也不会让它重新出现。

这就解释了你遇到的现象：**官方分组读取会话状态，没有检查“六行到底填回原表了没有”。** 早晨给三个工作 Bot 加的监督逻辑才负责核对这条业务验收标准。[Cindy 官方分组说明](https://github.com/makecindy/cindy/blob/043ea939e0b03da4c4d0d8db61dd9b2e90f00f88/docs/product-rules/task-inbox.md)

## 判断顺序

```
Failed → Running → 等机器 → 等人（工具调用）→ 等人（文字提问，分类器判断）→ 验证器通过？→ 达成 / 未达成
```

## 对照 Cindy 看出来的两个漏洞

两个 ⚠️ 都出在同一个地方：**Cindy 的分组只看会话状态，不看业务目标有没有达成。**

1. **3b 的软情况**：子任务只在回复文字里写了"缺链接"，然后正常结束。如果它是伙伴任务，就命中规则 5，**从收件箱消失了**。
    - **补法**：强制 agent 用 `ask_human` 提问；再加一个分类器扫最后一条回复，把漏掉的提问补成"待处理"。
2. **状态 5**：循环停了，但比如"六行还没填回原表"，Cindy 分不出来，伙伴任务同样会被隐藏。
    - **补法**：每个 session 创建时都带上验收标准，由你早上给三个工作 Bot 加的那套监督逻辑来核对。核对没通过，就主动把它重新推进"待处理"。

**一句话**：Cindy 管的是"session 停没停"，你的 superagent 管的是"事情做没做完"。两层都要有，人才能只看收件箱，不用回去翻 session。
